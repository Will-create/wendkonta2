# SalePro targeted follow-up — 15 November 2026

## Delivered behavior and causes corrected

- Product filters previously fetched an unfiltered page, then set quantities on
  non-matching products to zero. The existing data endpoint now filters its SQL
  query before counting/pagination, groups stock by the selected warehouse and
  preserves actual quantities. Search/category/advanced filters share one query;
  category and warehouse controls are visible above the list. Changing either
  reloads results immediately, resets the page and retains the search. Mobile
  cards prioritize product/code/category/quantity/unit/status/actions. Stock
  badges distinguish low stock, no stock and products without stock tracking.
- Finance → Accounts → Customer Accounts now opens a paginated customer account
  list with an authorized, direct **Faire un dépôt** button on every card. Cards
  show contacts, balance, sales, received payments/deposits, debt and credit.
  Debt, settlement and credit have both text and color indicators. Existing
  customer management remains available.
- Account summaries previously displayed only explicit `deposits`, although the
  historical statement already read original `payments`. Shared summaries now
  include original invoice payments in `received`, keeping explicit deposits
  separate. Deposit-transfer payments, including legacy casing variations, are
  not counted as new receipts. Totals use original payment rows rather than
  assuming that the editable `sales.paid_amount` cache proves receipt of money.
  Stored invoice discrepancies are reported, never corrected implicitly.
- Quick product creation reuses the existing eight-digit Keygen convention and
  generator endpoint. Generated codes are checked against product and variant
  codes; save validation checks uniqueness again. Manual codes remain editable;
  replacement requires consent and a pending response cannot overwrite a new
  edit. The existing save path is retained. A discovered save failure from an
  unconditional restaurant-only `menu_type` field was corrected.
- The quick modal now has a bounded flex layout: accessible header/footer,
  internally scrolling body, safe-area padding and dimensions driven by
  `visualViewport`, including keyboard height and viewport offset.
- The old `.dashboard-counts .row` two-column grid also affected chart rows.
  Only KPI rows now use that grid. Every dashboard chart has a dedicated sized
  frame; cash-flow/yearly canvases previously had none. Smartphone outer columns
  become full-width rows, while tablets/desktops retain their columns. Chart.js
  initializes responsively against the frame, disables fixed aspect ratios and
  receives size changes through ResizeObserver. No chart datasets/calculations
  were changed. Operational dashboard shortcuts follow the summary/charts.

## Financial convention and historical initialization

Historical ledger rows are a live projection of the existing source records,
identified by their original sale/payment/deposit IDs. No duplicate historical
cash/deposit rows are required or inserted. This makes initialization idempotent
and immediately exposes fully and partly paid historical sales after deployment.
Payment methods and related sale references appear in the statement.

- Received = original non-deposit-transfer invoice payments + unreversed account
  deposits. Reversal payments reduce the corresponding totals.
- Balance = received − completed sales in the configured base currency.
- Outstanding = invoice debts computed from actual payment rows, plus any
  unfunded deposit transfers.
- Available credit = unspent deposits + invoice overpayments.
- Balance = available credit − outstanding.

Existing cash-refund return semantics are retained: the return credit and its
cash payout appear separately and offset in the ledger. Foreign-currency
invoices remain explicitly identified and excluded from base-currency totals;
manual review is required rather than assuming an exchange conversion. The
report covers archived customers too; the operational card list shows active
customers within the user's permitted scope.

## Database changes and live reconciliation

**No new migration is needed for this follow-up. No production migration or data
change was performed.** The existing receipt-schema migration was used only to
prepare isolated compatibility copies of older backups for validation. Existing
migrations from the earlier transformation remain deployment prerequisites.

The new read-only command writes a private report under `storage/app/reports`:

```bash
php artisan customer-accounts:reconcile
```

For the existing Docker deployment, run on the host after updating its code:

```bash
docker compose -f /root/wendkonta/repo/deploy/compose.yaml exec -T --user 33:33 php php artisan customer-accounts:reconcile
```

The command loads the configured base currency/precision, includes original
payment/sale references, checks ledger balances and reports orphan/undated/
unmapped records. Exit 1 means review is required; it does not mean money was
moved or a migration was partially applied. Re-running it never inserts or
updates sales, invoices, payments, deposits or allocations.
